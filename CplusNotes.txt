C++ REFRESHER NOTES
===================


1. COMPILATION PIPELINE (a.cpp -> a)
-------------------------------------
  1. Preprocessing (g++ -E)
     Expands #include/#define/#ifdef, strips comments -> plain C++ text (.i)

  2. Compilation (g++ -S)
     Parses, type-checks, optimizes, lowers to human-readable assembly (.s)

  3. Assembly (g++ -c)
     Converts assembly to binary machine code, packaged as object file
     with unresolved symbols (.o)

  4. Linking (g++ a.o -o a)
     Resolves symbols against libraries (libstdc++/libc), merges into
     one runnable binary

  5. Running (./a)
     OS loader maps binary into memory, jumps to entry point; CPU runs
     native machine code directly, no runtime translation


2. VECTOR: operator[] VS .at()
-------------------------------
  - pop_back() only decrements size, does NOT clear/overwrite memory
    -> old value is physically still there at that address
  - v[i] does NO bounds checking -> reading past size() is UB; may
    "accidentally" show stale data instead of erroring
  - v.at(i) DOES bounds checking -> throws std::out_of_range if
    i >= size(), safer for catching real bugs
  - Lesson: never trust v[i] past size()-1 even if it prints something
    plausible; use .at() when unsure


3. BOOLEAN TRUTHINESS IN BITS
------------------------------
  - 0 (all bits 0) is false; ANY non-zero value (1, -1, 42, etc.) is
    true, not just 1
  - Applies to ints, pointers (nullptr/0 is false-y), and floats in
    if/while/&&/|| conditions


4. v.begin() AND v.end() -- WHERE THEY POINT
----------------------------------------------
  - v.begin() points TO the first element (index 0)
  - v.end() points ONE PAST the last element (a non-existent sentinel)
    -> *v.end() is UB
  - Example: size 12 (valid indices 0-11) -> begin()=index 0,
    end()=index 12 (invalid slot)
  - Get iterator to the actual last element: v.end()-1 (random-access)
    or --v.end(); or just use v.back() for the value
  - Why "one past": lets `for (i=begin(); i!=end(); ++i)` work cleanly
    without special-casing the last element


5. ITERATOR OPERATIONS
------------------------
  - *i dereferences -> value at that position
  - i++ / ++i moves next, i-- / --i moves previous
    (bidirectional+ containers: vector, list, set, map)
  - i + n jumps forward n (random-access only: vector, deque --
    NOT list/set/map). i < j position compare (random-access only)
  - i == j / i != j works for all iterator types -- the standard
    begin()/end() loop comparison
  - v.rbegin()/v.rend() = reverse iteration
  - v.cbegin()/v.cend() = const iterators, read-only
  - cout << i is INVALID (no operator<< for iterators) -> print *i
  - Prefer `auto i = v.begin();` over spelling out Container::iterator
    -- keeps code container-agnostic


6. POINTERS VS REFERENCES
---------------------------
  POINTERS
    int* p = &x;   (p holds the address of x)
    *p             dereferences to the value
    &x             address-of operator
    Can be reassigned (p = &y), can be null, supports arithmetic
    (p++, p+1 moves by sizeof(type) bytes), needs explicit * to access.

    Pros: nullable (optional-like), reassignable (iterators, linked
          structures), arithmetic (buffer traversal), required for
          new/delete and C APIs
    Cons: can be null/dangling (segfault/UB), easy to leak memory,
          verbose (* and -> everywhere), no guarantee of pointing to
          a valid object

  REFERENCES
    int& r = x;    (r is an alias for x, must bind at declaration)
    Use r directly, no * needed. &r == &x.
    Cannot be reassigned to refer elsewhere once bound. Cannot be null.
    No arithmetic (r++ increments the VALUE of x, not "moves").

    Pros: never null (safer), clean syntax, idiomatic for params
          (void f(vector<int>& v) avoids copies), const ref avoids
          copies while blocking mutation
    Cons: must init at declaration (no declare-now-bind-later), can't
          reseat (less flexible for linked list/tree repointing),
          no arithmetic

  WORKED EXAMPLE -- pointer and reference to the same memory:
    int val = 100;
    int *p = &val;        // p holds address of val
    int &ref = val;       // ref is just another NAME for val,
                          // no separate address

    &val == p == &ref     // all three addresses are IDENTICAL --
                          // ref is an alias, not a new object

    ref = 200;             // now val==200 and *p==200 too -> proves
                          // same memory location

  Key takeaway: a reference has no address of its own to inspect --
  &ref always equals &(the thing it refers to).


7. THE & OPERATOR (THREE MEANINGS, CONTEXT-DEPENDENT)
--------------------------------------------------------
  1. Address-of: `int *p = &val;` -- applied to an existing
     variable/expression, produces a pointer.
  2. Reference declarator: `int &ref = val;` / `void f(vector<int> &v);`
     -- appears in a TYPE, right after the type name, only in
     declarations.
  3. Bitwise AND: `int r = a & b;` -- between two integer values in
     an expression.

  How to tell apart: & right after a type name (int&, T&) = reference
  type. & before an existing variable in an expression (&val) =
  address-of.


8. BINARY SEARCH
------------------
  Loop condition: `while (start <= end)`, NOT `start < end`.
  Invariant: answer lies in [start, end] inclusive; start<=end means
  at least 1 element left to check. With start < end, when
  start==end (1 element left) the loop wouldn't run -> misses that
  element. Use start<end only for boundary-convergence patterns
  (lower_bound-style "first element >= target") where the loop
  deliberately stops once start==end, since that point IS the answer.

  Mid calc: `mid = start + (end - start) / 2`, NOT `(start+end)/2` --
  avoids integer overflow when start/end are near INT_MAX, since
  (end-start) is bounded by array size and never overflows. (Famous
  real bug: Java's binarySearch() had this for years.) Zero-cost
  habit, always use it.

  Standard template:
    int binarySearch(vector<int>& v, int target) {
        int start = 0, end = v.size() - 1;
        while (start <= end) {
            int mid = start + (end - start) / 2;
            if (v[mid] == target) return mid;
            else if (v[mid] < target) start = mid + 1;
            else end = mid - 1;
        }
        return -1;  // not found
    }


9. TREE TERMS: ANCESTOR, DESCENDANT, LOWEST COMMON ANCESTOR (LCA)
--------------------------------------------------------------------
  Family tree analogy:
    Grandpa -> {Dad, Uncle}
    Dad -> {You, Sister}
    Uncle -> {Cousin1, Cousin2}
    You -> YourKid

  Ancestor = someone ABOVE you (go up: parent, grandparent...).
    Your ancestors: Dad, Grandpa. Test: "in my direct 'up' lineage?"

  Descendant = someone BELOW you (opposite of ancestor).
    Grandpa's descendants: everyone else in the tree below him.

  LCA = the CLOSEST shared relative going up for two nodes.
    - You & Sister -> LCA=Dad (no need to go to Grandpa)
    - You & Cousin1 -> LCA=Grandpa (no shared parent, only meet
      at Grandpa)
    - You & YourKid -> LCA=You (YourKid is your descendant, you're
      your own ancestor here)
    Key nuance: "LOWEST" = CLOSEST/NEAREST, not "furthest back" --
    Grandpa is a common ancestor of nearly everyone, but only the
    correct LCA when no closer shared ancestor exists.

  In code: replace "family" with "tree nodes" -> LCA = point where
  upward paths from two nodes FIRST MEET. Used for distance between
  nodes (dist(X,Y) = depth(X)+depth(Y)-2*depth(LCA)), ancestor/
  descendant checks, path-between-nodes problems.

  Standard recursive LCA (binary tree, no parent pointers):
    TreeNode* lowestCommonAncestor(TreeNode* root, TreeNode* p, TreeNode* q) {
        if (root == nullptr || root == p || root == q) return root;
        TreeNode* left  = lowestCommonAncestor(root->left, p, q);
        TreeNode* right = lowestCommonAncestor(root->right, p, q);
        if (left && right) return root;   // p, q split -> root is LCA
        return left ? left : right;        // same subtree, or one found
    }
  Intuition: recurse both sides; a node getting non-null from BOTH
  calls means p and q are split across it -> it's their LCA.


10. DYNAMIC PROGRAMMING: RECURSION -> MEMOIZATION -> ITERATIVE
-----------------------------------------------------------------
  DP candidate signals: optimal substructure (solution built from
  subproblem solutions) + overlapping subproblems (same subproblem
  recomputed multiple times in naive recursion).

  Workflow, always in order:
    1. Write brute-force recursion first, don't jump to memoization.
    2. Identify the STATE -- minimal set of changing params that
       fully determines a subproblem's answer (state dimensions =
       memo table dimensions).
    3. Verify overlap actually exists (if none, memoization won't
       help).
    4. Add memo: check-cache-before-compute, store-after-compute.
    5. Optionally convert to bottom-up/iterative to avoid recursion
       overhead/stack overflow, then optimize space if only a fixed
       window of prior states is needed.

  Recursion -> memoization template (top-down):
    unordered_map<int,int> memo;   // or vector<int> memo(n+1, -1)

    int solve(int n) {
        if (/* base case */) return base_value;
        if (memo.count(n)) return memo[n];   // check cache first
        memo[n] = /* recursive computation using solve(smaller n) */;
        return memo[n];
    }
  Sentinel (-1) must be a value the real answer can never take; if
  answers can be negative, use a separate visited[] bool array
  instead. Time drops from exponential (e.g. O(2^n) naive Fibonacci)
  to O(n) -- each unique state computed once, repeats become O(1)
  cache hits.

  TOP-DOWN vs BOTTOM-UP
    Direction:   top-down starts big, recurses down.
                 bottom-up starts at base cases, iterates up.
    Stack:       top-down uses call stack (overflow risk for large n).
                 bottom-up has no recursion, no stack risk.
    Deriving it: top-down is easier -- just add cache lines to brute
                 force. bottom-up requires "flipping" the recurrence
                 direction.
    Work done:   top-down only computes states actually needed.
                 bottom-up computes every state up to n, even unused.

  Converting recursion -> iteration is NOT "same loop backward" -- it
  requires REDEFINING what each table entry means so dependencies
  flow in the iteration direction. Example (Climbing Stairs):
  top-down state solve(idx) = ways FROM idx TO the end (depends on
  future steps -> naturally recursive). Bottom-up state dp[idx] =
  ways FROM the start TO idx (depends on past steps -> naturally
  iterative, loop forward from 0). Base case flips: idx==n (top-down)
  becomes idx==0/1 (bottom-up) -- same recurrence, mirrored direction.
  (Both directions can be valid for symmetric recurrences -- what
  matters: pick a consistent meaning for dp[idx], ensure its
  dependencies are already computed, and loop in whichever direction
  satisfies that.)

  Space optimization: if dp[i] only depends on a FIXED small window
  of previous entries (e.g. just i-1, i-2), replace the full array
  with a few variables -> O(n) space becomes O(1). Only possible when
  the dependency window is bounded; if dp[i] needs ALL previous
  entries, the full table is required.

  Common DP bugs:
    - Wrong sentinel value (valid answers overlapping -1)
    - Off-by-one in memo sizing (n+1 vs n)
    - Memoizing on the WRONG state (two different param combos
      mapping to the same cell -> silently wrong cached answers)
    - Stale memo/map reused across separate top-level calls in a loop

  TERMINOLOGY IS PAIRED (DSA convention):
    Top-down  == Recursive + memoization
    Bottom-up == Iterative + tabulation


11. RECURSION DIRECTION: RECURSION ITSELF IS NOT INHERENTLY TOP-DOWN
------------------------------------------------------------------------
  Recursion is just "a function calling itself" -- top-down vs
  bottom-up behavior depends on WHERE the work happens relative to
  the recursive call (before vs after), not on recursion itself.

  TOP-DOWN recursion: work happens BEFORE recursing, state passed
  DOWN as params to children. Info flows root -> leaves.
    void topDown(TreeNode* root, int sum) {
        if (!root) return;
        sum += root->val;                  // work BEFORE recursing
        if (!root->left && !root->right) { use(sum); return; }
        topDown(root->left, sum);
        topDown(root->right, sum);          // pass state down
    }

  BOTTOM-UP recursion: recurse FIRST, combine/use results only AFTER
  calls return (need children's answers first). Info flows leaves
  -> root.
    int bottomUp(TreeNode* root) {
        if (!root) return 0;
        int left = bottomUp(root->left);
        int right = bottomUp(root->right);  // wait for children
        return 1 + max(left, right);        // combine AFTER
    }

  Most tree aggregate problems (height, diameter, balanced-check,
  path-sum aggregates) are naturally bottom-up. Problems tracking a
  running value downward (sum from root to current node, max
  ancestor seen so far) are naturally top-down.

  Cross-domain naming clash: DP's "top-down" (recursion+memo) is
  structurally the SAME shape as tree "bottom-up recursion" above
  (recurse first, combine after). DP names it by "which end you
  start reasoning from" (top-down = start at the big question); tree
  terminology names it by "when the combine step happens" (bottom-up
  = combine happens after). Same mechanics, different convention.


12. TREE RECURSION: THE 3-QUESTION FRAMEWORK
-----------------------------------------------
  Q1 -- "What does one call to this function tell me?" (THE
  CONTRACT.) State it in one plain sentence before writing code. If
  you can't state it, you're not ready to code yet.
    Example (height): "returns the height of the subtree rooted at
    this node."

  Q2 -- "What's the trivial case I already know without recursing?"
  (BASE CASE.) What breaks the pattern of having children to recurse
  into? Usually nullptr, sometimes specifically a LEAF -- depends on
  what the contract needs (see section 13).

  Q3 -- "If I had my children's answers, how do I build mine?"
  (COMBINE / recursive leap of faith.) Trust recursive calls already
  return correct answers per the contract -- don't unfold the whole
  call stack, just ask what to DO with left/right's results.
    Example (height): "1 + taller of my two children's heights" ->
    return max(1+left, 1+right).

  Q4 (only for GLOBAL aggregates, e.g. max diameter across the WHOLE
  tree, not just at the root) -- "Is what I ultimately want the SAME
  as what I return to my parent, or a side computation to capture
  separately?"
    - Same -> just return it (Max Depth).
    - Different -> need an ACCUMULATOR living OUTSIDE the normal
      return value (member var / ref param), while the function
      still returns per the contract.
    Example (Diameter): return value = height (parent needs it);
    separately, diameter = max(diameter, left_height+right_height)
    checked INSIDE the function at EVERY node (not just the root) --
    the longest path's peak could be any node.

  PROBLEM SHAPE CHEAT SHEET
    Pure bottom-up value (parent's answer = simple fn of children's,
    nothing else)               -> just return normally
                                    (Max Depth, Path Sum bool)
    Global aggregate + local    -> accumulator + normal return
    value (need "best across       per contract
    tree" AND per-node info)       (Diameter, Balanced check)
    Info flows both directions  -> pass extra params down,
    (down: running value;          return up (Path Sum with
    up: result)                    running remaining total)

  Common bug 1: computing the aggregate ONCE using only the root's
  children instead of updating the accumulator INSIDE the recursive
  function so EVERY node is checked as a potential "peak" (Diameter
  must take max(diameter, left+right) at every node, not just once).

  Common bug 2: calling a pure function like max(a,b) and DISCARDING
  the return value instead of assigning it back (`max(ans,x);`
  instead of `ans = max(ans,x);`). max() has no side effects -- any
  function that returns a value must have that value explicitly
  captured if needed.


13. LEAF vs NULL -- CRITICAL DISTINCTION FOR TREE BASE CASES
-----------------------------------------------------------------
  null = no node here at all (empty subtree)
  leaf = a node exists here with NO children
         (!root->left && !root->right)
  These get conflated because a leaf's children ARE null --
  recursing into a leaf's children hits the null base case. Bug: the
  null base case answering a question that only makes sense AT a
  leaf (e.g. "does this complete a valid root-to-LEAF path?").

  Before writing a base case, ask: "does this problem care about
  leaves SPECIFICALLY, or just empty subtrees?" Signal for a
  SEPARATE leaf check: the problem explicitly says "leaf" AND the
  answer depends on some accumulated condition (running sum)
  satisfied EXACTLY there.

  If a problem only asks about height/depth/count/structure (no
  explicit leaf semantics), null-sentinel + combining formula usually
  handles leaves automatically -- no special case needed (Max Depth,
  Diameter, Invert Tree, Count Good Nodes: 1+max(left,right) gives a
  leaf height 1 automatically since its children hit the null
  sentinel).

  BUG EXAMPLE (LeetCode 112, Path Sum -- root-to-LEAF path must sum
  to target):
    // WRONG: null base case does leaf-logic
    bool solve(TreeNode* root, int targetSum) {
        if (!root) return targetSum == 0;  // fires on ANY null
                                            // child, even of a
                                            // one-child node that
                                            // isn't a leaf!
        ...
    }
  Fails on 1 -> (right) 2, targetSum=1: solve(null,1-1=0) wrongly
  returns true, but the only real path (1->2, sum=3) doesn't match.
  Should be false.

    // CORRECT: explicit leaf check, separate from null check
    bool hasPathSum(TreeNode* root, int targetSum) {
        if (!root) return false;
        if (!root->left && !root->right)
            return targetSum == root->val;   // TRUE leaf check
        bool left  = root->left  && hasPathSum(root->left,  targetSum - root->val);
        bool right = root->right && hasPathSum(root->right, targetSum - root->val);
        return left || right;
    }
  Guard recursive calls with `root->left &&` / `root->right &&` so a
  missing child is never misread as a valid path ending.

  Technique: write a base-case TABLE before coding.
    Empty subtree (root==nullptr)      -> false
    Leaf (!left && !right)             -> targetSum==root->val
    Internal (otherwise)               -> left || right
  If only the empty-subtree row is needed, you likely don't need a
  separate leaf case.

  Sanity-check trees to hand-trace before trusting any tree recursion
  solution: single node (leaf itself); node with one real child + one
  null child (no leaf at root); node with two leaf children. The
  one-null-child-one-real-child tree is the MINIMAL case that
  exposes leaf-vs-null bugs -- always trace it by hand first.


14. MAJORITY ELEMENT DEFINITION (FLOOR(n/2) NUANCE)
-------------------------------------------------------
  "Appears more than floor(n/2) times" means count > floor(n/2), i.e.
  count >= floor(n/2)+1 -- strictly greater than the FLOORED half.
    Even n=6: floor(6/2)=3 -> need count>=4.
    Odd n=7:  floor(7/2)=3 -> need count>=4 (n/2=3.5 isn't
              achievable by an integer count anyway).

  This guarantee (a true majority always wins any 1-vs-all
  cancellation) is WHY Boyer-Moore Voting works -- no other
  element/combo can have enough occurrences to fully cancel the true
  majority out.
    int majorityElement(vector<int>& nums) {
        int candidate = nums[0], count = 0;
        for (int x : nums) {
            if (x == candidate) count++; else count--;
            if (count == 0) { candidate = x; count = 1; }
        }
        return candidate;
    }
  O(n) time, O(1) space -- no need to count against n/2, existence of
  a majority element under this definition is guaranteed.


15. STRING REVERSAL (STL)
----------------------------
  - reverse(s.begin(), s.end()) modifies IN PLACE, void return,
    O(n) time O(1) space. Works on string same as vector (both
    support iterators).
  - Reversed COPY without modifying original:
      string reversed(s.rbegin(), s.rend());
    Constructs a new string walking the original backward via
    reverse iterators, leaving s untouched.
  - Partial reversal: reverse(s.begin(), s.begin()+5) reverses only
    the first 5 characters.


16. CHAR LITERAL vs INT -- '0' IS NOT THE SAME AS 0
-------------------------------------------------------
  '0' is a CHAR LITERAL with numeric (ASCII) value 48, NOT 0.
  `int carry = '0';` silently sets carry to 48 -- easy to miss since
  it "looks like" zero-initialization.

  Always convert a char digit to its numeric value via
  `charDigit - '0'` (yields 0-9). Never treat a bare char literal as
  the integer 0 in arithmetic contexts.

  BUG EXAMPLE (Add Binary, LeetCode 67):
    int carry = '0';   // WRONG, starts at 48
    int carry = 0;      // CORRECT
  The bogus 48 compounds every iteration via sum = carry + ...,
  producing garbage multi-digit output instead of the correct binary
  sum.

  Reusable digit-string addition template (Add Binary base=2, Add
  Strings base=10, etc.):
    int sum = carry;
    if (i >= 0) sum += a[i--] - '0';
    if (j >= 0) sum += b[j--] - '0';
    ans.push_back('0' + (sum % base));
    carry = sum / base;
  Loop: `while (i >= 0 || j >= 0 || carry)` -- folding `|| carry` in
  handles a final trailing carry (e.g. "1"+"1"="10") automatically,
  no separate post-loop check needed. Also removes the need to
  manually swap a/b by length -- unequal lengths handled by the
  i>=0/j>=0 guards.


17. LOOP BOUNDARY OFF-BY-ONE: > 0 vs >= 0
---------------------------------------------
  `while (i > 0 || j > 0)` STOPS BEFORE processing index 0 -- index 0
  is still valid, meaningful data (the last item to process), not a
  sentinel to exclude.

  Correct condition when walking indices down to and including 0:
  `while (i >= 0 || j >= 0)` (plus `|| carry` if applicable, see
  section 16).

  The truly "nothing left" state is when the index goes NEGATIVE
  (< 0), not when it merely reaches 0 -- 0 is the last valid index of
  anything. Always double check > vs >= when looping down to
  array/string index 0.


18. SLOW/FAST POINTER TECHNIQUE: INITIAL POSITIONS + THE MATH
------------------------------------------------------------------
  Both slow and fast start at the SAME position -- head. Not offset
  from each other.
    ListNode* slow = head; ListNode* fast = head;

  WHY same start matters: the technique relies on a fixed SPEED RATIO
  (fast=2 nodes/iter, slow=1/iter). Starting together at a fixed
  ratio guarantees that when fast finishes traversing, slow has
  covered EXACTLY half the distance -- by construction. Offsetting
  the start (e.g. fast=head->next) keeps the 2:1 step ratio but
  breaks slow's final position from matching the true middle.

  THE MATH: list length = n. After k iterations, fast moved 2k
  nodes, slow moved k nodes. Loop ends when fast reaches the end:
  2k~=n -> k~=n/2. Since slow moved k~=n/2 nodes from the SAME start
  as fast, slow's final position IS the middle.

  General formula: if fast moves p steps per q steps of slow, slow
  lands at position n*(q/p) when fast finishes. For 2:1 (p=2,q=1):
  n*(1/2)=n/2. (A 3:1 ratio lands slow at the 1/3 point -- used in
  some "k-th fraction point" variations.)

  Standard template (LeetCode 876, Middle of Linked List):
    ListNode* middleNode(ListNode* head) {
        ListNode* slow = head, *fast = head;
        while (fast != nullptr && fast->next != nullptr) {
            slow = slow->next;
            fast = fast->next->next;
        }
        return slow;
    }

  ODD LENGTH (n=5, indices 0-4, true middle=index 2):
    iter1 fast 0->2, slow 0->1
    iter2 fast 2->4, slow 1->2
    check: fast=4, fast->next=null -> stop
    slow=index 2 -- exact middle, correct

  EVEN LENGTH (n=6, indices 0-5, LeetCode wants the SECOND
  middle=index 3):
    iter1 fast 0->2, slow 0->1 (continue, fast->next=3 valid)
    iter2 fast 2->4, slow 1->2 (continue, fast->next=5 valid)
    iter3 fast 4->6(null), slow 2->3
    check: fast=null -> stop
    slow=index 3 -- correct

  WHY the loop guard needs BOTH conditions
  (fast != nullptr && fast->next != nullptr):
  fast->next!=nullptr alone crashes on even-length lists (fast itself
  could be null, then fast->next is UB). fast!=nullptr alone crashes
  on odd-length lists (fast->next could be null while fast isn't,
  then fast->next->next dereferences null). Both together handle
  both parities safely.


19. BIT MANIPULATION: AND, OR, XOR, NOT, SHIFTS
---------------------------------------------------
  AND (&): result bit 1 only if BOTH input bits are 1.
    Uses: check odd/even (n&1), check bit i set (n & (1<<i)),
    masking (n & mask).

  OR (|): result bit 1 if EITHER input bit is 1.
    Uses: set bit i to 1 (n | (1<<i)), combine flags
    (flags = FLAG_A | FLAG_B).

  XOR (^): result bit 1 if input bits DIFFER.
    Properties: x^x=0, x^0=x, commutative + associative (order
    doesn't matter).
    Single Number (every element appears twice except one) -- XOR
    all elements, pairs cancel, unique remains:
      int singleNumber(vector<int>& nums) {
          int r=0; for (int x: nums) r^=x; return r;
      }
    Swap without temp: a^=b; b^=a; a^=b;
    Toggle bit i: n ^ (1<<i)

  WORKED EXAMPLE -- two numbers, all three operators at once
  (a=12, b=10):
    a = 12 = 1100
    b = 10 = 1010
    a & b  = 1000 = 8    (only bit position 3 has a 1 in BOTH)
    a | b  = 1110 = 14   (bit is 1 if EITHER has a 1 -- pos 1,2,3)
    a ^ b  = 0110 = 6    (bit is 1 only where they DIFFER -- pos 1,2;
                          position 3 matches (1,1) so it's 0)
  Use-case mapping: a&b -- checking which bits are common/shared
  between two flag sets. a|b -- merging two flag sets (union).
  a^b -- finding which bits differ between two states (detecting a
  toggled/changed bit, or isolating a "leftover" value after
  cancelling matching pairs).

  NOT (~): flips every bit in the FULL width (including sign bit) --
  ~5 on a 32-bit int is -6 (two's complement), not a small positive
  number. Don't expect it to invert "only the bits you care about."

  Left shift (<<): x<<n == x * 2^n. Common for building bitmasks:
  `1 << i` sets only bit i.

  Right shift (>>): x>>n == x / 2^n (floor division). Arithmetic
  (sign-preserving) shift for negatives on virtually all modern
  compilers.

  COMMON PATTERNS
    Power of 2 check: n > 0 && (n & (n-1)) == 0
      (power of 2 = single 1-bit; n-1 flips that bit and everything
      after to 1; AND gives 0 only if there was exactly one set bit)
    Count set bits: while (n) { n &= (n-1); count++; }
      (clears lowest set bit each time -> O(number of set bits)).
      Or __builtin_popcount(n) (GCC/Clang, O(1)-ish hardware-backed)
    Get/set/clear/toggle bit i:
      (n>>i)&1 / n|(1<<i) / n & ~(1<<i) / n^(1<<i)
    Missing Number (LeetCode 268):
      result = n; for i in 0..n-1: result ^= i ^ nums[i];
      (XOR-ing the full expected range against actual values cancels
      everything except the missing number)

  TRUTH TABLE
    (0,0) -> AND 0, OR 0, XOR 0
    (0,1) -> AND 0, OR 1, XOR 1
    (1,0) -> AND 0, OR 1, XOR 1
    (1,1) -> AND 1, OR 1, XOR 0

  Relevant DSA use cases despite feeling "separate": Single Number
  I/II/III, Counting Bits, Power of Two/Four, Subsets via bitmask
  enumeration (bit i = "include element i or not", enumerate 0 to
  2^n-1), DP with bitmask state (e.g. TSP-style problems).

  Gotchas: right-shifting negative numbers is implementation-defined
  pre-C++20 for exact rounding but arithmetic shift is universal in
  practice. `1 << 31` overflows signed 32-bit int (UB) -- use
  `1u << 31` or `1LL << 31` if that range is needed.


20. lower_bound AND upper_bound -- DEFINITIONS + EXAMPLE
------------------------------------------------------------
  lower_bound(target) = first element >= target
  upper_bound(target) = first element > target (strictly greater,
                          excludes exact match)

  Example, sorted {10, 20, 30, 40}:
    lower_bound(20) -> 20 (exact match included)
    upper_bound(20) -> 30 (exact match skipped, next bigger)
    lower_bound(25) -> 30 and upper_bound(25) -> 30 (identical when
      no exact match exists -- both just return the next bigger
      element)

  Two forms: member functions on set/map/multiset (O(log n), use
  tree structure directly) vs <algorithm> free functions on a sorted
  vector/array (`lower_bound(v.begin(), v.end(), x)`, O(log n) binary
  search). Free-function form gives a silently WRONG answer (not a
  crash) if called on an unsorted range -- always ensure the range is
  sorted first.

  Always check `it != s.end()` (or `!= v.end()`) before dereferencing
  -- if target is bigger than everything, both return end().

  Mnemonic: lower_bound = lower/left boundary of where target fits
  -> includes exact matches. upper_bound = upper/right boundary ->
  position just past all elements equal to target, so exact matches
  are skipped.


21. SORT COMPARATOR: MUST USE STRICT <, NEVER <= (STRICT WEAK ORDERING)
---------------------------------------------------------------------------
  std::sort (and priority_queue, set, map, etc.) requires the
  comparator to satisfy STRICT WEAK ORDERING: comp(x, x) must ALWAYS
  return false for any element x. This is a hard mathematical
  requirement the algorithm's internals depend on, not a style
  choice.

  Using <= breaks this: comp(x, x) becomes `x.second <= x.second` ->
  always TRUE -- directly violates the contract.
    // WRONG -- violates strict weak ordering
    sort(dist.begin(), dist.end(), [](pair<int,int> &a, pair<int,int> &b){
        return a.second <= b.second;
    });

    // CORRECT
    return a.second < b.second;

  Why it "works" on small inputs but crashes/misbehaves on large
  ones: introsort (quicksort/heapsort/insertion-sort hybrid used by
  std::sort) uses the comparator's guarantees to decide
  partitioning/recursion. With a broken comparator, a<b and b<a can
  both appear true for equal elements -- on large inputs (many
  duplicate keys), this leads to out-of-bounds internal array access
  -> segfault/heap corruption (libstdc++), not just "wrong order."
  Small inputs may not happen to trigger the bad access pattern.

  <= is NOT recoverable via lambda captures, const-ref params, or any
  rewrite -- the issue is the mathematical property of <= itself when
  applied reflexively (x<=x is always true), not a syntax/capture
  problem. There is no valid way to use <= in a comparator.

  - If the goal was "ties are fine, don't care about their order" --
    plain < already allows this; sort doesn't guarantee any specific
    order among equal elements.
  - If the goal was "preserve original relative order among ties" --
    use stable_sort instead of sort, but STILL with strict <.
  - If the goal was an explicit tie-breaker (e.g. sort by distance,
    then by original index) -- use a compound comparator, strict <
    at every level:
      sort(dist.begin(), dist.end(), [](const pair<int,int> &a, const pair<int,int> &b){
          if (a.second != b.second) return a.second < b.second;
          return a.first < b.first;      // tie-break by original index
      });

  General rule: ANY custom comparator passed to sort/priority_queue/
  set/map must use strict < (or > for descending) -- never <= or >=.


22. PRIORITY QUEUE / HEAP -- FULL REFERENCE
-----------------------------------------------
  Header: #include <queue>
  (priority_queue lives here, NOT in a header named after itself)

  HEAP vs PRIORITY QUEUE -- concept vs implementation
    Heap = a CONCEPT/technique: a complete binary tree (every level
    full except possibly the last, filled left-to-right) satisfying
    the HEAP PROPERTY: every parent >= both children (max-heap) or
    <= both children (min-heap). "Heap" is not a specific class name
    -- it's a category of structure satisfying this property.

    Priority Queue = an ABSTRACT DATA TYPE / behavior contract: "give
    me the highest-priority element fast, let me insert new elements,
    let me remove the highest-priority one." Could theoretically be
    implemented several ways (unsorted array: O(n) find-max, O(1)
    insert; sorted array: O(1) find-max, O(n) insert) -- a binary
    heap gives the best balance: O(1) find-max, O(log n)
    insert/remove. THAT is why priority_queue is implemented
    internally using a heap.

    Relationship: same as vector (concrete class) implementing
    "dynamic array" (the concept) -- priority_queue is the concrete
    STL class, heap is the technique it uses internally.

  INTERNAL DATA STRUCTURE
    A binary heap stored in a flat vector<T> -- NO pointers at all.
    Parent/child relationships computed by index arithmetic:
      parent(i)      = (i - 1) / 2
      left child(i)  = 2*i + 1
      right child(i) = 2*i + 2

    Example max-heap [9,5,8,1,3,7] as a tree:
              9(0)
             /    \
           5(1)   8(2)
          /   \    /
        1(3) 3(4) 7(5)

    Root (index 0) is always the max (or min) by the heap property.
    Why vector (not pointer-based tree): cache-friendly contiguous
    memory, no per-node pointer overhead, O(1) amortized append/
    shrink at the end (which push/pop rely on).

  TEMPLATE SIGNATURE -- 3 parameters
    priority_queue<T, Container, Compare>

    T (1st)         = element type (int, pair<int,int>, custom
                       struct, etc.)
    Container (2nd) = underlying storage, defaults to vector<T>.
                       This is NOT "max-heap vs min-heap" -- it is
                       purely the data structure holding the
                       elements. Must support random access +
                       push_back/pop_back/front (vector or deque
                       qualify; list does NOT, no random access). In
                       practice: ALWAYS just use vector<T> (or omit
                       and take the default).
    Compare (3rd)   = comparison logic, defaults to less<T> (produces
                       MAX-heap, counterintuitively -- the convention
                       makes the LARGEST element rise to the top).

    You can put ANY type in a heap, including pair<int,int> or custom
    structs, as long as it has < defined or you supply a custom
    comparator.

  MAX-HEAP (default) -- largest element on top
    priority_queue<int> maxHeap;
    maxHeap.push(5); maxHeap.push(1); maxHeap.push(9); maxHeap.push(3);
    maxHeap.top();   // 9
    maxHeap.pop();   // removes 9
    maxHeap.top();   // 5

  MIN-HEAP -- smallest element on top. Must specify all 3 template
  args (can't skip the 2nd to override only the 3rd):
    priority_queue<int, vector<int>, greater<int>> minHeap;
    minHeap.push(5); minHeap.push(1); minHeap.push(9); minHeap.push(3);
    minHeap.top();   // 1

  COMMON COMPILE ERROR: writing `priority_queue<int, greater<int>>`
  (only 2 args) -- the compiler tries to interpret greater<int> as
  the CONTAINER (2nd slot), fails because greater<int> has no
  value_type (it's a comparator, not a container). Error: "no type
  named 'value_type' in 'std::greater<int>'". Fix: always write all
  3 args for a min-heap.

  PAIRS AND CUSTOM COMPARATORS (very common for DSA -- e.g.
  {distance, index}, {value, listIndex}):
    priority_queue<pair<int,int>> maxHeap;
    // max-heap by .first, then .second

    priority_queue<pair<int,int>, vector<pair<int,int>>, greater<pair<int,int>>> minHeap;
    // min-heap by .first, then .second

    // fully custom comparator via lambda (needs decltype since
    // lambda types are unique per-instance):
    auto cmp = [](const pair<int,int>& a, const pair<int,int>& b) {
        return a.second > b.second;   // min-heap by .second
    };
    priority_queue<pair<int,int>, vector<pair<int,int>>, decltype(cmp)> pq(cmp);

  Comparator convention: cmp(a,b)==true means "a has LOWER priority
  than b" (a sits below b in the heap, gets popped later). This can
  feel inverted vs writing an ascending sort() comparator -- for
  min-heap-by-second use `a.second > b.second` (note: >, not < --
  this is the flip that trips people up).

  METHODS -- comparison with queue and stack
    push(x)   queue:yes  priority_queue:yes  stack:yes
              insert; O(1) queue/stack, O(log n) heap
    pop()     queue:yes  priority_queue:yes  stack:yes
              void return in ALL three -- never returns a value
    front()   queue:yes  priority_queue:NO   stack:NO
              queue only -- priority_queue has no front()
    back()    queue:yes  priority_queue:NO   stack:NO
              queue only
    top()     queue:NO   priority_queue:yes  stack:yes
              priority_queue/stack use top(), not front()
    empty()   queue:yes  priority_queue:yes  stack:yes
    size()    queue:yes  priority_queue:yes  stack:yes

  priority_queue has NO iterators -- no .begin()/.end(), can't
  range-for over it, can only ever see top(). To inspect all elements
  you must pop everything (destroying the heap) or use a different
  container.

  push() MECHANICS -- "bubble up" / "sift up"
    Append new element to the END of the vector (keeps tree
    complete), then repeatedly compare it to its parent and swap if
    it violates the heap property, moving up one level per swap
    until the property holds or the root is reached. O(log n) since
    heap height is log n.

    Trace inserting 10 into max-heap [9,5,8,1,3,7]:
      append -> [9,5,8,1,3,7,10] (index 6)
      parent(6)=2 -> value 8; 10>8 -> swap -> [9,5,10,1,3,7,8] (idx 2)
      parent(2)=0 -> value 9; 10>9 -> swap -> [10,5,9,1,3,7,8] (root, stop)

  pop() MECHANICS -- "bubble down" / "sift down"
    Move the LAST element in the vector to the root (index 0),
    shrink the vector by one, then repeatedly compare the new root
    to its children and swap with the more "extreme" child (larger
    for max-heap) if the property is violated, moving down one level
    per swap until the property holds or a leaf is reached. O(log n).

    Trace popping max from [10,5,9,1,3,7,8]:
      move last (8) to root -> [8,5,9,1,3,7]
      children of idx0: idx1=5, idx2=9; 9 larger -> swap with idx2
        -> [9,5,8,1,3,7] (now at index 2)
      children of idx2: idx5=7 (idx6 doesn't exist); 8>7, property
        holds -> stop

  COMPLEXITY SUMMARY
    top()            O(1)
    push()           O(log n)
    pop()            O(log n)
    overall storage  O(n)

  COMPARISON -- priority_queue (heap) vs plain vector vs sorted
  vector, for "repeatedly get the max/min" workloads:

    Unsorted vector:
      find max/min: O(n) scan | insert: O(1) push_back |
      remove max/min: O(n) (find then erase)
      Best for: rarely -- one-off max lookups only

    Sorted vector (kept sorted):
      find max/min: O(1) (ends) | insert: O(n) (shift to insert in
      place) | remove max/min: O(n) shift, or O(1) if only removing
      from an end
      Best for: static data, few inserts, many range queries (also
      gives lower_bound/upper_bound, which heap does NOT)

    priority_queue (heap):
      find max/min: O(1) top() | insert: O(log n) | remove max/min:
      O(log n)
      Best for: REPEATED insert + remove-max/min interleaved -- the
      classic "top-k" / "streaming" / "always need current best"
      workload

  If you only need the max ONCE with no further inserts, even an
  unsorted vector + single O(n) scan (max_element) beats building a
  heap for no reason.

  TOP-K PATTERN MNEMONIC (using a bounded-size heap)
    "k SMALLEST" -> use a MAX-heap of size k: push every element, if
      size>k pop (evicts the current largest of your top-k
      candidates, keeping the k smallest). Example: K Closest Points
      to Origin.
    "k LARGEST" -> use a MIN-heap of size k: push every element, if
      size>k pop (evicts the current smallest). Example: Kth Largest
      Element in a Stream.
  This bounded-heap technique gives O(n log k) time, O(k) space --
  better than a full O(n log n) sort when k << n.

  COMMON BUGS
    - Confusing less<T> default with min-heap (it's actually
      max-heap)
    - Comparator direction backwards (cmp returning true = "lower
      priority", easy to invert by habit from sort())
    - Calling .pop() expecting a return value (void, same as
      stack/queue)
    - Trying .front()/.begin() on a priority_queue (doesn't exist,
      compile error)
    - decltype(cmp) requires the lambda variable to be declared
      first, can't inline a lambda directly into the template
      parameter list


23. INORDER TRAVERSAL -- DEFINITION, ITERATIVE IMPLEMENTATION, AND BST VALIDATION USE
------------------------------------------------------------------------------------------
  DEFINITION: Inorder traversal visits a binary tree in the order:
    LEFT subtree -> CURRENT node -> RIGHT subtree
  (recursively applied at every node). For a Binary Search Tree
  specifically, inorder traversal visits nodes in SORTED ASCENDING
  order -- this is the property that makes it useful for BST
  validation (see below).

  RECURSIVE VERSION (for contrast):
    void inorder(TreeNode* root, vector<int>& ans) {
        if (!root) return;
        inorder(root->left, ans);
        ans.push_back(root->val);
        inorder(root->right, ans);
    }

  ITERATIVE VERSION (using an explicit stack instead of the call
  stack):
    void iterative(TreeNode* curr, vector<int>& ans) {
        stack<TreeNode*> st;

        while (curr || !st.empty()) {
            // curr indicates the node that needs to be processed.
            // we validate it and then add it to the stack
            while (curr) {
                st.push(curr);
                curr = curr->left;
            }
            TreeNode* node = st.top(); st.pop();
            ans.push_back(node->val);
            curr = node->right;
        }
    }

  HOW TO READ THIS LOGIC (the key insight):
    - The inner while loop's job is to walk all the way down the
      LEFT spine from `curr`, pushing every node along the way onto
      the stack (deferring processing -- "I'll come back to you
      after I've gone as far left as possible").
    - Once `curr` becomes null (no more left children), the
      leftmost unprocessed node is sitting on top of the stack --
      pop it, that's the next node to VISIT (record its value).
    - After visiting a node, move to its RIGHT subtree (`curr =
      node->right`) and let the outer loop repeat: if that right
      subtree has its own left spine, the inner loop walks down it
      again before the next visit.
    - The outer loop condition `curr || !st.empty()` covers both
      "there's still a subtree to walk down" (curr non-null) AND
      "there's still a deferred node waiting to be visited" (stack
      non-empty) -- traversal isn't done until BOTH are exhausted.
  This mirrors the recursive version exactly: the stack manually
  plays the role that the call stack would automatically play in
  the recursive version (remembering "go back to this parent after
  finishing its left subtree").

  Time: O(n) -- every node pushed and popped exactly once.
  Space: O(h) for the explicit stack (h = tree height), same as the
  recursion depth would be in the recursive version.

  USE CASE -- LeetCode 98, Validate Binary Search Tree:
    Since inorder traversal of a valid BST produces values in
    STRICTLY ASCENDING order, validating a BST reduces to: perform
    an inorder traversal, and check that each visited value is
    strictly greater than the previous one. If any value is <= the
    previous one, the tree is NOT a valid BST.

    bool isValidBST(TreeNode* root) {
        stack<TreeNode*> st;
        TreeNode* curr = root;
        long prev = LONG_MIN;   // sentinel smaller than any valid node value

        while (curr || !st.empty()) {
            while (curr) {
                st.push(curr);
                curr = curr->left;
            }
            TreeNode* node = st.top(); st.pop();
            if (node->val <= prev) return false;   // must be strictly increasing
            prev = node->val;
            curr = node->right;
        }
        return true;
    }
  Why this works: this is the exact same iterative inorder skeleton
  above, with one added check at the "visit" step -- instead of just
  recording the value, compare it against the previously visited
  value. Because inorder visits nodes in the exact order a valid BST
  requires them to be sorted, a single linear pass is enough; no need
  to build a separate array and sort/check it afterward.
  Using LONG_MIN (not INT_MIN) as the sentinel guards against a valid
  node value equal to INT_MIN incorrectly failing the check, given
  the problem's node value constraints can reach INT_MIN/INT_MAX.


24. GRAPH / GRID BFS: MARK VISITED AT PUSH TIME, NOT POP TIME
-------------------------------------------------------------------
  BFS vs DFS -- CORE DIFFERENCE: the order you visit nodes in.
  BFS uses a QUEUE to visit the CLOSEST nodes first (explores level
  by level, outward in rings from the start). DFS skips past nearby
  nodes and follows a single path all the way
  until it hits a dead end, before backtracking to try others.

  CLASSIC BUG ("delayed marking"): marking a cell/node as visited
  when it's POPPED from the queue, instead of when it's PUSHED.

    // WRONG -- marks on pop
    while (!q.empty()) {
        auto [i, j] = q.front(); q.pop();
        grid[i][j] = VISITED;          // <-- too late
        for (each neighbor (nx, ny))
            if (grid[nx][ny] == UNVISITED)
                q.push({nx, ny});
    }

  WHY IT'S WRONG: a cell can have MULTIPLE unvisited neighbors still
  in the queue at the same time, all pointing back to it. Since the
  cell isn't marked visited until it's popped, every one of those
  neighbors sees it as still "unvisited" and pushes it AGAIN before
  it's ever processed. Same cell ends up enqueued multiple times.

  Concrete example: a 2x2 block of land, all connected --
    (1,1) has two neighbors, (0,1) and (1,0). If you mark on pop,
    both can push (1,1) before its first copy is popped.

  IMPACT: queue size balloons well past O(m*n) (duplicate entries
  for the same cells), degrading what should be an O(m*n) BFS into
  something far slower -- classic cause of TLE on dense/large grids
  in flood-fill style problems (e.g. LeetCode 200, Number of
  Islands). Can also cause double-counting bugs in problems that
  tally something per visited cell/node.

  FIX -- mark visited AT PUSH TIME (including the very first,
  starting node):
    q.push({start_i, start_j});
    grid[start_i][start_j] = VISITED;      // mark immediately

    while (!q.empty()) {
        auto [i, j] = q.front(); q.pop();
        for (each neighbor (nx, ny))
            if (grid[nx][ny] == UNVISITED) {
                grid[nx][ny] = VISITED;     // mark BEFORE pushing
                q.push({nx, ny});
            }
    }
  Now each cell is enqueued exactly once -- true O(m*n) time, O(m*n)
  worst-case space (max queue size, e.g. a solid block of land).

  RULE OF THUMB: in BFS, "visited" must be set at the moment a
  node/cell is ADDED to the queue, never deferred to when it's
  removed. This applies to any BFS over a graph or implicit grid
  graph, not just island-counting -- same bug/fix pattern shows up in
  shortest-path BFS, multi-source BFS, etc.



25. GRAPH REPRESENTATIONS: ADJACENCY LIST vs ADJACENCY MATRIX
----------------------------------------------------------------
  V = Number of Vertices (nodes), n in most problem statements
  E = Number of Edges (connections), edges.size() in most problems

  ADJACENCY MATRIX -- 2D array approach
    vector<vector<int>> graph(n, vector<int>(n, 0));
    graph[u][v] = 1;  // edge from u to v

    Structure: n×n matrix where graph[i][j]=1 means edge i->j exists,
    0 means no edge. For undirected graphs, symmetric (graph[i][j] ==
    graph[j][i]).

    SPACE: O(V²) -- ALWAYS allocates n² cells regardless of actual
    edge count.
      Example: 10,000 nodes with 100 edges still allocates
      100,000,000 cells, using only 200 of them.

    TIME:
      Check if edge exists: O(1) -- direct array access graph[u][v]
      Get all neighbors of vertex i: O(V) -- must scan entire row
        for (int j=0; j<n; j++)
            if (graph[i][j] == 1) { /* j is a neighbor */ }
      Add edge: O(1)
      BFS/DFS neighbor iteration: O(V) per vertex -> O(V²) total
        even if only E edges exist

    Use cases (rare):
      - Dense graphs where E ≈ V² (nearly every pair connected)
      - Need O(1) edge-existence checks very frequently
      - Algorithms like Floyd-Warshall (all-pairs shortest paths)
        that inherently iterate V² pairs

  ADJACENCY LIST -- vector of vectors approach
    vector<vector<int>> graph(n);  // n empty vectors
    graph[u].push_back(v);         // add edge u->v
    graph[v].push_back(u);         // undirected: add reverse too

    Structure: array of V dynamic lists, graph[i] holds only the
    ACTUAL neighbors of vertex i.

    SPACE: O(V + E)
      - Outer structure: V empty vectors (one per vertex)
      - Inner elements: total across all vectors = 2E for undirected
        (each edge stored twice), E for directed
      Breakdown:
        graph[0] = [1, 2]       // 2 elements
        graph[1] = [0, 3]       // 2 elements
        graph[2] = [0, 3, 4]    // 3 elements
        graph[3] = [1, 2, 4]    // 3 elements
        graph[4] = [2, 3]       // 2 elements
        Total: 5 (outer) + 12 (inner) = 17 units for V=5, E=6

    WHY "V + E" NOT "V × E": We ADD the space for structure (V
    vectors) and the space for data (sum of all inner sizes = 2E).
    In a matrix, every one of V rows has V columns -> multiply.
    In a list, each of V vectors has a DIFFERENT size (its degree),
    and the SUM of those sizes equals the total edge count.

    TIME:
      Check if edge exists: O(degree of u) -- linear search in
        graph[u] for v (can be O(V) worst case for a hub node). Use
        unordered_set<int> instead of vector<int> for O(1) average
        lookup if needed.
      Get all neighbors of vertex i: O(degree of i) -- iterate only
        graph[i]
        for (int neighbor : graph[i]) { /* process */ }
      Add edge: O(1) amortized (vector push_back)
      BFS/DFS neighbor iteration: O(degree) per vertex -> O(E) total
        across entire traversal (each edge checked at most twice for
        undirected)

    Use cases (99% of graph problems):
      - Sparse graphs (E << V²) -- real-world graphs are nearly
        always sparse
      - BFS, DFS, shortest path algorithms (Dijkstra, Bellman-Ford)
      - Most LeetCode/interview graph problems

  COMPARISON TABLE
  | Operation            | Adjacency Matrix | Adjacency List    |
  |----------------------|------------------|-------------------|
  | Space                | O(V²)            | O(V + E)          |
  | Check edge exists    | O(1)             | O(degree) / O(V)  |
  | Get all neighbors    | O(V)             | O(degree)         |
  | Add edge             | O(1)             | O(1)              |
  | BFS/DFS total        | O(V²)            | O(V + E)          |

  REAL-WORLD IMPACT (LeetCode constraint example: V ≤ 2×10⁵, E ≤ 2×10⁵)
    Matrix: 2×10⁵ × 2×10⁵ = 4×10¹⁰ ints ≈ 160 GB (impossible, OOM)
    List:   2×10⁵ + 4×10⁵ = 6×10⁵ ints ≈ 2.4 MB (fits easily)

  STANDARD TEMPLATE (LeetCode 1971, Find if Path Exists in Graph)
    bool validPath(int n, vector<vector<int>>& edges, int source, int destination) {
        if (source == destination) return true;

        // Build adjacency list: O(V + E) space
        vector<vector<int>> graph(n);
        for (auto& edge : edges) {
            graph[edge[0]].push_back(edge[1]);
            graph[edge[1]].push_back(edge[0]);
        }

        // BFS
        queue<int> q;
        vector<bool> visited(n, false);

        q.push(source);
        visited[source] = true;

        while (!q.empty()) {
            int curr = q.front();
            q.pop();

            if (curr == destination) return true;

            // Only iterate actual neighbors: O(degree) per vertex
            for (int neighbor : graph[curr]) {
                if (!visited[neighbor]) {
                    visited[neighbor] = true;  // mark at push time (see section 24)
                    q.push(neighbor);
                }
            }
        }

        return false;
    }

  KEY OPTIMIZATIONS vs naive matrix approach:
    1. Visited tracking: separate bool array instead of modifying
       graph in-place (graph[i][j]=-1 pollutes the structure)
    2. Neighbor iteration: for-each loop over graph[curr] instead of
       scanning all n vertices with `for(int j=0; j<n; j++)`
    3. Early termination: return immediately when destination found,
       don't wait to exhaust the queue

  COMMON BUGS
    - Forgetting to add BOTH directions for undirected graphs
      (graph[u].push_back(v) AND graph[v].push_back(u))
    - Using graph.size() when you meant graph[i].size() (outer size
      vs inner size)
    - Trying to access graph[u][v] like a matrix when graph[u] is a
      list -> compile error or logic bug (v is an index into the
      neighbor list, not a vertex ID check)
    - Not initializing visited array, or reusing a stale one across
      multiple BFS/DFS calls in a loop
